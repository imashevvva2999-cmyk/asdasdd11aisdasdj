## Решения по OQ-55–58

### OQ-55 — Glass-навигация: **закрыто ✅, одобрено с ограничениями**

**Решение:** вводим premium glass-эффект на существующую нижнюю пилюлю.

**Что сохраняется без изменений:** форма пилюли, размеры (`PILL_HEIGHT`), позиция (floating, `insets.bottom + PILL_BOTTOM_GAP`), spacing, иконки, поведение навигации, **уже существующий (незакоммиченный) анимированный индикатор активной вкладки и icon-transition** — glass добавляется только на фоновый слой пилюли, не заменяет и не трогает indicator/иконки/лейблы.

#### Технический план (предложение, не реализация)

- Фон пилюли: `BlurView` из `expo-blur` (уже зависимость, уже используется в `bottom-sheet.tsx` и `toast.tsx` — переиспользуем те же конвенции intensity/tint, не изобретаем новые с нуля) вместо сплошного `backgroundColor: '#141418'`.
- Поверх blur — полупрозрачный tint-слой с нижней границей непрозрачности (не ниже ~60–70%), чтобы текст/иконки оставались читаемыми поверх ярких обложек, прокручивающихся за пилюлей.
- Hairline-граница (`borderColor: 'rgba(255,255,255,0.08)'` сейчас) делаем чуть заметнее для контраста на светлом фоне — не glow, не neon.
- **Явно избегаем:** избыточной прозрачности, glow/свечения, визуального шума — как и требует решение.

#### Какие экраны показывают навигацию (проверено по текущей структуре роутов)

Уже сегодня, без изменений, пилюля показывается **только** на `(tabs)/home`, `(tabs)/search`, `(tabs)/library` и их вложенных стек-экранах (See All, Liked Songs, Search Results, Search Genre, All Genres — все внутри группы `(tabs)`). Она уже отсутствует на: полном плеере (`player/now-playing`), всех `sheets/*` (модалки), Album/Artist/Playlist/Track, Profile и её артист-подмаршрутах, Create Playlist. **Это уже соответствует требованию «which full-screen experiences should intentionally hide it» без изменений в коде** — фиксируем как явное правило, а не меняем.

**Будущее исключение:** Artist Dashboard (OQ-56) как отдельный опыт тоже не должен показывать слушательскую пилюлю — будет своя навигация (см. ниже).

#### Производительность и safe area (требования к тестированию)

- `backdrop-filter`/`BlurView` на iPhone Safari исторически дороже и менее стабильно поддерживается, чем в Chrome — **обязательная проверка**: скролл Home с видимой пилюлью, не проседает ли FPS.
- Safe-area уже корректно обрабатывается через `useSafeAreaInsets()` — изменений не требует.

**⏸ Контрольная точка:** реализация Фазы 2 (ниже) требует отдельного «можно начинать» после того, как пользователь увидит этот план.

### OQ-57 — Вертикальный Discovery: **закрыто ✅, только изолированный preview**

**Решение:** исследуем TikTok-style вертикальный discovery, **не интегрируя в продакшен** пока. Ниже — все 6 запрошенных артефактов.

#### 1. Предложение точки входа

Отдельная, явно видимая точка входа **рядом** с баннером Late Night Flow, не на самой поверхности баннера — баннер уже имеет 3 живых тап-таргета (весь-карточка onPress, Play, Next — последний добавлен вчера, не закоммичен), и добавление жеста прямо на баннер рискует с ними конфликтовать. Предлагается небольшой контрол под/рядом с баннером (например текстовая подсказка-чип «Discover» со стрелкой вверх), который **тапом** (не жестом) открывает новый экран — это и есть «explore entry through the existing wave interaction» без изменения самого баннера.

#### 2. Концепция экрана

Полноэкранный вертикальный пейджер, один трек = один «слайд»: обложка на весь экран (затемнённая/размытая подложка), название трека/артиста и состояние воспроизведения поверх — визуальный язык (типографика, палитра) тот же, что у существующего горизонтального carousel, но full-bleed вертикально. Swipe up → следующий трек, swipe down → предыдущий.

#### 3. Анализ конфликта жестов

Текущий горизонтальный swipe (`artwork-carousel.tsx:87-122`) **строго ограничен осью X** (`activeOffsetX`, `failOffsetY`) — новый вертикальный экран на **отдельном роуте** никогда не монтируется одновременно с ним, конфликта нет в принципе (разные экраны = разный scope жестов в React Navigation). Expand/collapse жест плеера — тоже отдельный оверлей, не пересекается. **Единственная точка внимания:** вход в новый экран должен быть тапом, а не жестом (пункт 1), чтобы не создавать неоднозначность с жестом разворачивания мини-плеера.

#### 4. Спецификация аудио-поведения

- Использует **тот же** общий player store / audio engine — никакого второго плеера (неизменное требование проекта).
- Переход между треками — через существующий паттерн `swipeTo()`/debounce (`SWIPE_AUDIO_DELAY_MS`), чтобы быстрые свайпы не «дёргали» audio engine.
- Треки без demo-аудио показывают **то же самое** честное состояние «No audio in this preview», что уже проверено в разделе 2.1 — никакой имитации воспроизведения.
- Loading-состояние — тот же `playback: 'loading'`, что и везде в приложении.

#### 5. План изолированного preview

Строится как dev-only роут (тот же паттерн, что `dev-ui-kit.tsx` — автоматически вырезается из продакшен-сборки `scripts/web-postexport.mjs`), **не привязан** к реальному баннеру Home. Доступен только по прямой ссылке/dev-входу. Это и есть «NOT integrating into the production application yet».

#### 6. Критерии приёмки для iPhone Safari

- Плавный свайп 60fps с momentum/snap к треку.
- Аудио-переходы без щелчков/обрывов между треками.
- Честное «нет аудио» состояние рендерится идентично существующему паттерну (пункт 4).
- Жест не конфликтует с нативным pull-to-refresh/bounce-скроллом Safari (нужна проверка `overscroll-behavior`).
- Safe-area соблюдена сверху/снизу.
- С `prefers-reduced-motion` — переключение без анимации (snap), не плавный свайп.

**Честность по каталогу (прямое требование пользователя):** 13 треков, 2 играбельных — preview **не выдаёт себя за полноценную ленту**. Рекомендация: явная демо-рамка (например видимая пометка «Preview» на неиграбельных треках, тот же честный подход, что уже используется в остальном приложении) вместо добавления новых каталожных данных на этом этапе.

**⏸ Контрольная точка:** даже постройка изолированного preview (Фаза 3 ниже) требует отдельного «можно начинать» — решение выше одобряет только *план*, не постройку.

### OQ-58 — Локализация: **закрыто ✅, три языка (ru/en/ky)**

**Решение:** полная многоязычность — русский, английский, киргизский.

#### Архитектура (предложение, библиотеки не устанавливаются)

- Рекомендуемая библиотека: `i18next` + `react-i18next` — стандартный зрелый выбор для связки React Native + React Native Web, единый API на обеих платформах, поддержка namespace’ов и ленивой загрузки. Это будет **первая новая зависимость** за всё время этого трека работ — требует отдельного одобрения на установку при переходе к реализации.
- Структура: `src/locales/{ru,en,ky}/<namespace>.json`, namespace на каждую область (`common`, `home`, `search`, `library`, `player`, `profile`, `sheets`, `artist-dashboard` — последний появится вместе с OQ-56).
- **Персистентность выбора языка:** в текущем проекте **ни один store не использует persist-слой** (проверено для раздела 1.3 этого аудита) — локаль будет первым использованием этого паттерна, аналогично рекомендации для Like-персистентности в Фазе 0.
- **Определение языка / fallback:** на первом запуске — локаль устройства через `expo-localization` (сейчас не зависимость, потребует добавления); если локаль устройства не ru/en/ky — fallback на русский (основной язык документации проекта); дальше — явный переключатель в настройках (сейчас отдельного экрана настроек нет — нужно будет создать точку входа, скорее всего в Profile).
- **Длинные переводы:** русский и киргизский обычно длиннее английского — при извлечении строк нужно проверять компоненты с фиксированной шириной на переполнение; существующий паттерн `numberOfLines`/`ellipsizeMode` (уже используется в `TrackRow` и др.) — основная защита, но не везде достаточна (кнопки с фиксированной шириной — отдельный риск).
- **Собственные имена:** имена артистов, названия треков/альбомов остаются как в данных (сейчас — английские) и **не переводятся автоматически** — только если в моках появятся явные локализованные поля.
- **Киргизские глифы:** нужна визуальная проверка, что Ң/Ө/Ү корректно рендерятся в Inter/Plus Jakarta Sans на используемых начертаниях — реальная задача, не предположение.
- **Охват:** все слушательские экраны, будущий Artist Dashboard (OQ-56), notifications, меню, empty-состояния — согласно запросу. Вчерашние незакоммиченные файлы (`home/index.tsx`, `search/index.tsx`, `library/index.tsx`, `floating-tab-bar.tsx`) тоже попадут в охват, когда до них дойдёт очередь извлечения строк.
- **Для новых фич — сразу без хардкода:** начиная с Фазы 0 этого плана, новые строки стоит сразу оборачивать в `t('key')`-конвенцию (даже до полной миграции легаси-строк), чтобы не наращивать долг дальше — пользователь прямо просит «avoid hardcoded user-facing strings in new features».

#### План роллаута (фазы внутри Фазы 5, см. ниже)

1. Инфраструктура: установка i18next-семьи, скелет locale-файлов, персистентность, определение языка — **без замены строк**.
2. Извлечение + перевод самых демо-критичных экранов первыми (Home, Search, Library, Player, навигация).
3. Остальные экраны и sheets.
4. Строки Artist Dashboard — по мере постройки (OQ-56).
5. QA-проход: переполнение layout на длинных переводах + проверка киргизских глифов.

**⏸ Контрольная точка:** даже шаг 1 (инфраструктура, без замены строк) требует отдельного «можно начинать» — установка новой зависимости явно не одобрена этим решением («Do not install libraries... yet»).

### Фаза 1 — Mood & Vibe Mixes: премиальные анимации
**Содержание:** 4 прототипа в `dev-ui-kit.tsx` → ревью пользователем → интеграция.

- **Зависимости:** вчерашняя незакоммиченная CSS-база (`mood-visual.web.tsx`) как основа.
- **Риск регрессии:** низкий — прототипы изолированы до интеграции.
- **Тестирование:** визуальное ревью в dev-kit → повторная проверка на реальном устройстве после интеграции.

**⏸ Контрольная точка (дважды: после прототипов, и отдельно — после ревью, перед интеграцией).**

### Фаза 2 — Glass-навигация (план готов, см. OQ-55)
- **Зависимости:** вчерашний незакоммиченный индикатор активной вкладки — glass накладывается, не заменяя его.
- **Риск регрессии:** средний — производительность `backdrop-filter` на Safari, контраст поверх разного контента.
- **Тестирование:** FPS при скролле на iPhone Safari, контраст поверх светлой/тёмной обложки.

**⏸ Контрольная точка.**

### Фаза 3 — Vertical Discovery: изолированный preview (план готов, см. OQ-57)
- **Зависимости:** существующий, протестированный `gesture-math.ts`.
- **Риск регрессии:** отсутствует для продакшена — изолированный dev-only роут по дизайну.
- **Тестирование:** ручная проверка отсутствия конфликта жестов с горизонтальным carousel/плеером, swipe-производительность на iPhone Safari.

**⏸ Контрольная точка.**

### Фаза 4 — Artist Dashboard: отдельный опыт (план готов, см. OQ-56)
- **Зависимости:** решение OQ-56 (закрыто); Stitch-референс для Analytics (**OQ-59, открыто**).
- **Риск регрессии:** низкий для нового (изолированный навигатор) — **средний** для переноса существующего содержимого `dashboard.tsx` в новую табовую оболочку (единственное место, где трогается уже рабочий код).
- **Тестирование:** слушательская навигация не затронута; существующие ссылки/роуты на Dashboard по-прежнему резолвятся после переноса.

**⏸ Контрольная точка.** Analytics конкретно дополнительно ждёт OQ-59.

### Фаза 5 — Локализация (архитектура готова, см. OQ-58)
- **Зависимости:** **новая npm-зависимость** (i18next-семья) — первая за весь трек работ.
- **Риск регрессии:** высокий при поспешной реализации (в итоге трогает каждый экран) — смягчается строго поэтапным роллаутом (инфраструктура → демо-критичные экраны → остальное → Dashboard → QA), никогда не одним большим диффом.
- **Тестирование:** проход по каждой локали вручную, проверка переполнения layout на длинных переводах, проверка киргизских глифов.

**⏸ Контрольная точка на каждом из 5 под-шагов роллаута отдельно.**
