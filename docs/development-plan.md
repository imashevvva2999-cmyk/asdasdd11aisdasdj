## Фаза 1 — Настройка проекта
**Цель:** рабочий каркас монорепозитория, CI, стандарты.
- git-репозиторий, монорепо (pnpm + Turborepo), структура из `architecture.md` §7.
- Expo-приложение (TypeScript, Expo Router, ESLint, Prettier, strict TS).
- [Доп, по OQ-53] Оценка подхода ко второй поверхности (WebView в MBANK): общий код с мобильным клиентом (React Native Web) или отдельная сборка — решение фиксируется до начала Фазы 3.
- NestJS-приложение, PostgreSQL и Redis в docker-compose для локальной разработки.
- `packages/shared` — OpenAPI-контракт v0; генерация клиента.
- `packages/design-tokens` — токены из DESIGN.md.
- CI: lint, typecheck, unit-тесты на каждый PR; EAS Build для dev-сборок.
- Управление секретами (`.env.example`, без секретов в репозитории).
- **Результат:** «Hello Mmusic» на iOS и Android с тёмной темой; API `/health`; зелёный CI.

## Фаза 2 — Core UI (дизайн-система)
**Цель:** UI-кит, точно соответствующий Nocturne Audio.
- Шрифты Plus Jakarta Sans и Inter; типографическая шкала; цвета; радиусы; отступы; blur и свечения.
- Компоненты: кнопки (все типы из `screens.md` §3.3), чипы, тумблеры, поля ввода, карточки (§3.4), строки списков (§3.5), секция с «See All», hero, бейджи, скелетоны, тосты, bottom sheet, пустое состояние, экран ошибки.
- Витрина компонентов (Storybook или экран-галерея) для визуальной сверки с макетами.
- **Результат:** все компоненты с тестами снапшотов, сверены с макетами дизайнером.

## Фаза 4 — Музыкальный каталог

- **Результат:** каталог просматривается полностью; данные из API, а не захардкожены.

## Фаза 5 — Плеер
**Цель:** надёжное воспроизведение — ядро продукта.
- Аудио-сервис на react-native-track-player: очередь из контекста, Play/Pause, Next/Prev, seek, Shuffle, Repeat (off/all/one).
- Фон, lock screen, гарнитура, прерывания (звонок), смена аудиовыхода.
- Мини-плеер (канонический вариант по OQ-28), Now Playing (S-15) со свечением по цвету обложки.
- Lyrics (S-16) с синхронизацией; Queue (S-17) с drag-and-drop и Infinity Autoplay.
- Предзагрузка следующего трека, gapless, crossfade, нормализация (по скоупу OQ-31).
- Отправка событий воспроизведения (батчи, офлайн-ретраи).
- **Результат:** 1 час непрерывного воспроизведения в фоне без сбоев на iOS и Android.

## Фаза A — Artist Flow (кабинет артиста и публикация треков)
> Добавлено 2026-10-06, по утверждённому флоу **Profile Hub → Become an Artist (S-25) → Artist Setup (S-26) → Artist Dashboard (S-27) → Upload Track (S-28)**, см. `docs/user-flow.md` UF-14.

**Цель:** дать существующему слушателю стать артистом и опубликовать трек в существующем каталоге — без отдельного приложения, отдельной модели треков или отдельного плеера.
**Зависит от:** Фаза 3 (навигация — экраны встраиваются в стек профиля, как S-24 Settings), Фаза 4 (модель каталога / Track), Фаза 5 (плеер — опубликованные треки должны играть без доработок плеера), Фаза 7 (переиспользуемые паттерны формы и загрузки обложки из Create Playlist, S-14).
**Блокирующие вопросы:** OQ-48 (привязка счёта для выплат), OQ-50 (состояния публикации трека). Не блокируют фазу, но должны быть учтены: OQ-49 (верификация артиста), OQ-51 (таб-бар кабинета — отложено), OQ-52 (формулировка «Artist Insights»).
**Вне скоупа (не проектируется и не реализуется):** Mmusic Studio, Mmusic Boost, Midnight Mirage, аналитика по трекам, платное продвижение, payouts, подписка/тарифы артиста, отдельная навигация Overview / Analytics / Catalog / Payouts.

1. **Artist/User:** связь `Artist.ownerUserId ↔ User` (1:1, architecture.md §6); эндпоинт создания артиста из текущей сессии; проверка «пользователь уже артист».
2. **Become an Artist — навигация:** пункт в Profile Hub (S-23) → S-25; для пользователя, уже являющегося артистом, переход сразу на S-27 (см. [Доп] в `screens.md`, S-23).
3. **Artist Setup (S-26):** форма (сценическое имя, жанр, био, город, фото), валидация, создание Artist.
4. **Artist Dashboard (S-27):** метрики Listeners / Streams / Support (на основе существующих событий воспроизведения и донатов), список «Your Releases» (переиспользует Track row), фильтры All / Published / In Review, без таб-бара Overview/Analytics/Catalog/Payouts.
5. **Upload Track (S-28) — форма:** поля Title, Artist / Featured Collaborators, Genre, Release Settings (Now / Schedule), Explicit.
6. **Файл и обложка:** выбор аудиофайла с устройства; превью и замена обложки — переиспользует паттерн из Create Playlist (S-14, Фаза 7).
7. **Track ownership:** связь нового Track с Artist через существующую `TrackArtist`; серверная проверка владения при любом изменении или удалении трека артистом.
8. **Upload/publishing states:** минимальная реализация (happy-path) на компонентах дизайн-системы; полный набор состояний uploading/processing/success/error — **только после ответа на OQ-50**.
9. **Интеграция с каталогом и плеером:** опубликованный трек проходит тот же пайплайн, что и остальной каталог (architecture.md §3.1, §5.1); появляется в поиске, на S-08/S-09; играет в существующем плеере без изменений плеера.
10. **Валидация и тестирование:** unit-тесты владения (артист не может редактировать/удалять чужой трек), E2E UF-14 (Maestro), ручная сверка S-25…S-28 с дизайном.

**Результат:** UF-14 проходит целиком на реальных (или контрактных) данных; опубликованный трек воспроизводится как обычный трек каталога; существующий функционал слушателя не затронут.

## Фаза 8 — Backend-интеграция
(Идёт параллельно с фазами 2–7.)
- Модули `auth`, `users`, `catalog`, `search`, `library`, `playlists`, `playback`, `recommendations`, `analytics` (architecture.md §3.2).
- Схема БД и миграции (architecture.md §6).
- Пайплайн контента: загрузка → FFmpeg-транскодинг в HLS → LUFS → объектное хранилище → CDN; подписанные URL.
- Импорт каталога от поставщика (OQ-04); простой инструмент для редакции.
- Рекомендации v1: правила + коллаборативная фильтрация; ежедневные миксы в полночь.
- Наблюдаемость: логи без PII, метрики, трейсинг, алерты.
- **Результат:** клиент переключён с моков на реальный API; контрактные тесты зелёные.

## Фаза 9 — Интеграция с банком
- Вход: OIDC / передача сессии из MBANK (OQ-07), refresh, logout, «сессия истекла».
- Донаты: S-19 → S-20 → биометрия (OQ-15) → S-21; ввод своей суммы (T-03); ошибки платежа (T-05); идемпотентность; аудит-лог.
- История поддержки (S-22), квитанции (OQ-16), email-дайджест (если в скоупе).
- Аналитика банка (OQ-35); при положительном решении — подписка (OQ-05) и офферы банка.
- **Результат:** донат проходит end-to-end в sandbox банка, без двойных списаний; все ошибки обработаны.

## Фаза 10 — Тестирование
- Unit и компонентные тесты (цель ≥ 80% для бизнес-логики, плеера, донатов).
- Интеграционные тесты API; контрактные тесты клиент ↔ сервер.
- E2E (Maestro): все сценарии UF-01…UF-14 из `user-flow.md` (включая UF-14 Artist Flow).
- Тесты плеера на реальных устройствах (матрица iOS/Android, Bluetooth, CarPlay/Android Auto — если в скоупе).
- Нагрузочное тестирование API и CDN; тест старта воспроизведения < 1.5 с.
- Безопасность: SAST, проверка зависимостей, пентест по требованиям банка (OQ-36), MASVS.
- Доступность: VoiceOver / TalkBack.
- UAT с заказчиком; визуальная сверка с дизайном.
- **Результат:** нет открытых критических и высоких дефектов; все критерии приёмки §13 пройдены.

## Фаза 11 — Подготовка к релизу
> Деплой и публикация **не выполняются** без отдельного разрешения заказчика.
- Конфигурации окружений (dev / stage / prod), runbook, план отката.
- Материалы для сторов (мобильное приложение) **и** пакет интеграции/встраивания для MBANK (WebView-поверхность) — подтверждено 2026-10-06, нужны оба.
- Политика конфиденциальности, Terms, Audio Licenses (ссылки есть в S-24).
- Release candidate, чек-лист релиза, мониторинг и алерты.
- **Результат:** RC готов; решение о публикации — за заказчиком.
