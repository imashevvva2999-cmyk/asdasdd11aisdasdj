## 2. React #418 — причина и предложение (ничего не менялось)

Исследование показало **два класса одной причины**. Статический HTML собирается при экспорте и не знает того, что есть только в адресе. Клиент при гидратации рисует другое дерево, и React выдаёт #418.

| Класс | Маршруты | Что в статическом HTML | Что рисует клиент |
|---|---|---|---|
| **A. Параметры в адресе** (`?…`) | `/search/results?q=…`, `/sheets/options?kind=&id=`, `/sheets/add-to-playlist?trackId=`, `/sheets/support?artistId=` | Состояние без параметров: «Nothing to show.», «Artist not found.», трек по умолчанию, пустой поиск | Реальное содержимое по параметрам |
| **B. Динамические страницы, не собранные заранее** | например `/artist/kaelen`, `/album/nebula-dreams`, `/playlist/late-night-driving` | Заранее собирается один ID на маршрут (`solaris-echo`, `horizon-deluxe`, `late-night-flow`); остальные отдаются общей оболочкой с «… not found» | Нужного артиста / альбом / плейлист |

**Доказательства:**
- По классу A статический HTML одинаков с параметрами и без. Сервер (`scripts/serve-web.mjs`) выбирает файл по пути, а Expo Router при экспорте строит маршрут без query-строки.
- Экраны, которые читают параметр только в эффекте (Now Playing) или в обработчике (Create Playlist), гидратируются чисто.
- В `main` все 7 маршрутов дают ту же ошибку. Сверено с эталонной сборкой `main`.

**Пользователь видит** правильное содержимое: React перерисовывает страницу. Но в консоли ошибка, а при холодной загрузке такого адреса на короткое время виден «чужой» каркас.

### Предлагаемое безопасное исправление (на утверждение)

- **Класс A — вариант 1 (рекомендую).**
  - Новый хук `useHydratedSearchParams()`: пока идёт гидратация, он возвращает пустые параметры (как статический HTML), а сразу после — реальные. Основан на уже исправленном `useHydrated` (`useSyncExternalStore`).
  - Подключить в 4 экранах. В Search Results дополнительно перемонтировать поле поиска по `q`, потому что начальное значение читается один раз.
  - Изменение поведения: при холодной загрузке адреса с параметрами на один кадр виден каркас без параметров. При переходах внутри приложения ничего не меняется.
  - Затрагивается 5 файлов.
- **Класс A, отвергнутые варианты:**
  - проверка гидратации внутри каждого экрана — больше правок и меняет проверку маршрутов;
  - `suppressHydrationWarning` — не исправляет различия в структуре.
- **Класс B.** Собирать заранее все ID из каталога (`generateStaticParams` в `artist/[id]`, `album/[id]`, `playlist/[id]`, `search/genre/[id]`). Поведение в браузере не меняется, растёт число HTML-файлов в сборке. Для будущих данных с бэкенда то же решение, что для класса A: каркас при гидратации, затем данные.
- **Проверка исправления:** браузерная проверка 37 маршрутов (в том числе с параметрами и другими ID) с нулём ошибок #418, плюс проверка, что нужное содержимое появилось.
- **Где делать:** на ветке `w3-stage1-iphone`. В `main` старая версия `useHydrated` дала бы мигание при каждом открытии листа.
