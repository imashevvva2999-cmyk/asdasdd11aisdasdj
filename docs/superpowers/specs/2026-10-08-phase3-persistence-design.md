# Фаза 3 — Сохранение данных: техническая спецификация

**Статус:** на утверждении. Пакеты не устанавливаются, код не меняется до одобрения.
**Дата:** 2026-10-08. **Основа:** коммит `77594cb` (Фаза 2).

## 1. Цель и критерии успеха

Сейчас все пользовательские данные живут только в памяти (Zustand) и теряются при перезагрузке страницы или перезапуске приложения. Цель — сохранять их локально на устройстве, не мешая будущей серверной синхронизации.

Критерии успеха:
1. После перезагрузки браузера (Expo Web) и перезапуска приложения (Expo Go) восстанавливаются:
   - лайкнутые песни;
   - созданные плейлисты и их состав;
   - изменения состава собственных плейлистов;
   - подписки на артистов и сохранённые альбомы и плейлисты;
   - отметки «скачано»;
   - подписки на жанры;
   - выбранные настройки Library.
2. Повреждённые или устаревшие данные не ломают приложение: оно запускается с корректным состоянием, а пользователь теряет минимум данных.
3. Данные из будущей версии схемы (откат приложения) не перезаписываются.
4. Нет мигания: экран Library не показывает сначала стартовые данные, а потом сохранённые.
5. Слой хранения заменяем: будущий бэкенд подключается без переписывания экранов.

Вне области:
- синхронизация с сервером;
- несколько аккаунтов;
- шифрование;
- сохранение позиции воспроизведения и очереди;
- история поддержки артистов (§3.3).

## 2. Оценка: Zustand `persist` + `@react-native-async-storage/async-storage`

### 2.1. Версия пакета

- Expo SDK 57 закрепляет **`@react-native-async-storage/async-storage@2.2.0`** (`node_modules/expo/bundledNativeModules.json`). `npx expo install` поставит именно её.
- Последняя версия в npm — 3.1.1, но она:
  - на Web использует IndexedDB вместо `localStorage`;
  - требует отдельный конфиг-плагин;
  - не входит в набор модулей SDK 57 (риск для Expo Go).
- **Рекомендация: 2.2.0.**

### 2.2. Совместимость

| Платформа | Хранилище в 2.2.0 | Проверено |
|---|---|---|
| Expo Web | `window.localStorage`, обёрнутый в Promise | Исходник 2.2.0 (`lib/module/AsyncStorage.js`, прочитан на unpkg, без установки) |
| Статический рендер Web (`web.output: "static"`, Node) | `window` отсутствует → вызовы отклоняются Promise'ом, без падения при импорте | По исходнику; дополнительно защищаемся в адаптере (§4.2) |
| iOS / Android (Expo Go) | Нативное хранилище; модуль входит в Expo Go SDK 57 | Нативно не проверить — симуляторов нет |

Ограничения Web:
- лимит `localStorage` около 5 МБ на источник (наши данные — десятки КБ);
- в приватном режиме некоторых браузеров запись может бросать `QuotaExceededError` (обрабатываем, §6);
- данные видны в DevTools и **не шифруются**.

### 2.3. Zustand `persist` (Zustand 5.0.15, уже в проекте)

Даёт нужные возможности без новых зависимостей:
- `createJSONStorage`;
- `version` + `migrate`;
- `partialize`;
- `merge`;
- `onRehydrateStorage`;
- `hasHydrated`;
- `skipHydration`.

Особенности, которые нужно учесть:
- **`persist` пишет при каждом `setState`**, даже если сохраняемая часть не изменилась. Плеер обновляет состояние 4 раза в секунду (Фаза 2), поэтому без защиты лайки перезаписывались бы непрерывно. Мера: адаптер пропускает запись, если строка не изменилась (§4.2).
- `Set` не сериализуется в JSON — сохраняем массивы, восстанавливаем `Set` в `merge`.
- Гидратация асинхронная на всех платформах — первый рендер идёт со стартовым состоянием (§4.5).

### 2.4. Альтернативы (отклонены)

| Вариант | Почему нет |
|---|---|
| `react-native-mmkv` | Быстрее, но требует development build — не работает в Expo Go |
| `expo-sqlite` / `kv-store` | На Web нужна сборка wasm и настройка Metro — избыточно для простых списков |
| Прямой `localStorage` | Только Web; на телефоне понадобилось бы второе решение |
| `expo-secure-store` | Шифрует, но нет Web и малый лимит значения; оставляем для будущих секретов (токены), не для библиотеки |

**Вывод:** Zustand `persist` + `async-storage@2.2.0` подходит для Expo Web и Expo Go при условии адаптера из §4.2.

## 3. Что сохраняется

### 3.1. Сохраняется

| Домен | Источник (store) | Сохраняемые поля | Ключ |
|---|---|---|---|
| Лайки | `player-store` | `likedTrackIds` (массив, порядок = порядок добавления) | `mmusic:<userId>:likes` |
| Библиотека | `library-store` | `items` (kind, refId, addedAt), `downloadedIds`, `followedGenreIds` | `mmusic:<userId>:library` |
| Плейлисты | `playlists-store` | созданные пользователем плейлисты целиком; для собственных стартовых (`editorial !== true`) — только `trackIds` | `mmusic:<userId>:playlists` |
| Настройки Library | новый `library-prefs-store` | сортировка Library, вид список/сетка, сортировка Liked Songs | `mmusic:<userId>:library-prefs` |

«Подписки на артистов и альбомы» в коде — это элементы `library-store.items` с `kind: 'artist' | 'album' | 'playlist'`. Кнопки Follow и Save пишут туда же, поэтому отдельного хранилища не нужно.

`userId` — id текущего mock-пользователя (`currentUser` в `src/mocks/user.ts`). С появлением авторизации MBANK ключи разделятся по аккаунтам без миграции формата.

### 3.2. Предлагается дополнительно (решение пользователя, §11)

| Домен | Источник | Рекомендация |
|---|---|---|
| Настройки приложения (качество, crossfade, переключатели) | `settings-store` | Сохранять — маленький объект, ожидаемое поведение |
| Недавние поиски | локальное состояние `search/index.tsx` | Сохранять — нужен вынос в store |
| Активный фильтр Library (All/Playlists/…) | локальное состояние | Не сохранять — это навигация, а не предпочтение |

### 3.3. Не сохраняется (и почему)

- **Очередь, текущий трек, позиция, `playback`** — после перезапуска плеер честно начинает с `idle`. Восстановление «последнего трека» — отдельная функция позже.
- **История поддержки (`support-store`)** — финансовые данные банковского контекста. Источник истины — бэкенд MBANK; на устройстве в открытом виде не храним.
- **Профиль артиста и загруженные треки (`artist-store`)** — отдельный поток с моковым каталогом; не входит в объём Фазы 3.
- **Состояние уведомлений** — демо-данные (OQ-27).
- **Производные значения** (`trackCount`, `durationLabel`, `updatedLabel`) — вычисляются при загрузке.

## 4. Архитектура

### 4.1. Модули

```
src/lib/persistence/storage.ts      адаптер StateStorage над AsyncStorage (SSR-защита, кэш записей, ошибки)
src/lib/persistence/keys.ts         имена ключей: mmusic:<userId>:<domain>
src/lib/persistence/validate.ts     ручные проверки формы (без новых зависимостей)
src/lib/persistence/snapshots.ts    типы сохраняемых снимков (DTO) + parse/serialize для каждого домена
src/state/*-store.ts                persist(...) с version, partialize, merge, migrate, onRehydrateStorage
src/state/library-prefs-store.ts    новый маленький store настроек Library
src/hooks/use-stores-hydrated.ts    true, когда все сохраняемые store загружены
```

Экраны не меняют API: они по-прежнему вызывают `toggleLike`, `toggleSaved`, `createPlaylist` и т. д.

### 4.2. Адаптер хранения

```ts
export function createAppStorage(backend: AsyncStorageLike | null): StateStorage
```

- **SSR и отсутствие хранилища:** на Web без `window` (статический рендер) или без доступа к `localStorage` используется хранилище в памяти. Приложение работает, просто без сохранения.
- **Пропуск одинаковых записей:** кэш последней записанной строки по ключу; при совпадении `setItem` не вызывается.
- **Ошибки записи** (`QuotaExceededError`, приватный режим):
  - перехватываются;
  - один раз пишется предупреждение в консоль (в dev);
  - состояние в памяти продолжает работать.
- **Внедрение зависимости:** тесты в Node передают хранилище в памяти, то есть реальный адаптер без нативного модуля. Это тот же подход, что `AudioEngine` в Фазе 2.

### 4.3. Формат записи

Конверт `persist` по умолчанию: `{ state, version }`.

`state` — снимок домена (DTO), а не состояние store:
```ts
type LibrarySnapshotV1 = {
  items: { kind: 'playlist' | 'album' | 'artist'; refId: string; addedAt: string }[];
  downloadedIds: string[];
  followedGenreIds: string[];
};
type LikesSnapshotV1 = { tracks: { trackId: string; likedAt: string }[] };
type PlaylistsSnapshotV1 = {
  created: { id: string; title: string; description?: string; coverKey?: string;
             trackIds: string[]; isPublic: boolean; isCollaborative: boolean;
             createdAt: string; updatedAt: string }[];
  trackEdits: Record<string, { trackIds: string[]; updatedAt: string }>; // собственные стартовые плейлисты
};
type LibraryPrefsSnapshotV1 = { sortMode: 'Recently Added' | 'Alphabetical'; gridView: boolean; likedSortMode: TrackSortMode };
```

**Обложки.** `coverUri` созданного плейлиста — результат `require()`: на нативе это номер модуля, на Web — объект с URL сборки. Между сборками это значение меняется, поэтому сохраняется стабильный `coverKey` (например, `sample-3`) и при загрузке сопоставляется с `sampleImageChoices`. Неизвестный ключ → обложка по умолчанию (`CoverFallback`).

**Время.** `addedAt`, `likedAt`, `createdAt`, `updatedAt` — ISO 8601 UTC. Нужны для будущего слияния с сервером. Лайки получают `likedAt` (сейчас это просто `Set`).

### 4.4. Первый запуск и стартовые данные

- **Ключа нет** (первый запуск) → стартовые mock-данные, как сейчас. Они сохраняются при первом изменении.
- **Ключ есть** → сохранённые данные — источник истины. Например, если пользователь снял лайк со стартового трека, после перезапуска лайк не вернётся.
- **Стартовые (каталожные) плейлисты не копируются в хранилище.** Сохраняются только созданные пользователем плейлисты и `trackIds` собственных стартовых. Обновление каталога не конфликтует с локальными данными.

### 4.5. Гидратация без мигания

- Root layout уже возвращает `null`, пока не загружены шрифты. Условие расширяется: `fontsLoaded && storesHydrated`.
- На Web чтение `localStorage` занимает миллисекунды. На нативе — десятки мс, их скрывает splash screen.
- Предел ожидания — 1,5 с. Если хранилище не ответило, приложение показывается со стартовым состоянием, а сохранённые данные применяются после загрузки.
- Совпадение серверного HTML (статический рендер) и первого клиентского рендера не нарушается: гидратация происходит после первого рендера.

## 5. Проверка и восстановление данных

Проверка выполняется на границе системы — при чтении из хранилища (`merge`), без новых зависимостей (`validate.ts`).

| Ситуация | Поведение |
|---|---|
| Ключа нет | Стартовые данные |
| Невалидный JSON | Сырое значение копируется в `<ключ>:corrupt` (один экземпляр, перезаписывается), ключ сбрасывается, используются стартовые данные, предупреждение в dev-консоль |
| Форма снимка неверна целиком | Как невалидный JSON |
| Отдельные записи невалидны (не тот тип, пустой id) | Отбрасываются только они, остальные сохраняются |
| Ссылка на несуществующую сущность каталога (трек, альбом, артист, жанр удалён из mock-каталога) | Запись отбрасывается при загрузке |
| Дубликаты | Сводятся к одной записи (самая ранняя дата) |
| `version` меньше текущей | `migrate` — пошаговые функции v1→v2→…; при ошибке миграции — как невалидный JSON |
| `version` больше текущей (откат приложения) | Данные **не читаются и не перезаписываются**: store работает только в памяти, запись блокируется до обновления приложения |

## 6. Ошибки хранилища во время работы

- Запись не удалась (квота, приватный режим) → данные продолжают работать в памяти; предупреждение в dev-консоль один раз.
- Пользовательского сообщения на этом этапе нет. [П] Позже можно показывать тост «Changes can't be saved on this device».
- Чтение не удалось → как «ключа нет», но запись в этот ключ блокируется до следующего успешного чтения, чтобы не затереть данные, которые просто не прочитались.

## 7. Совместимость с будущим бэкендом

1. **Только идентификаторы.** Сохраняются id каталога и пользовательские поля. Данные каталога (названия, обложки, длительности) не дублируются, кроме созданных пользователем плейлистов, у которых нет серверной копии.
2. **Локальные id.** Новые плейлисты получают префикс `local-` (сейчас `user-playlist-<время>`; меняется на `local-playlist-<uuid>`). При синхронизации сервер вернёт постоянный id, и локальный будет переназначен.
3. **Время изменений** у каждой записи — основа для слияния (last-write-wins или правила сервера).
4. **Ключи по пользователю** (`mmusic:<userId>:…`) — выход из аккаунта или смена пользователя очищает свои ключи (`clearUserData(userId)`).
5. **Граница:** экраны работают только со store. Сервер позже подключается одним из двух способов: заменой адаптера на «локальный кэш + очередь отправки» или загрузкой с сервера с последующим `merge`. Экраны не меняются.
6. **Безопасность:** в хранилище нет токенов, платёжных и персональных данных, кроме содержимого библиотеки. Будущие секреты хранятся в `expo-secure-store`.

## 9. Тесты и проверка

**Автотесты** (`scripts/verify-persistence.mjs`, `tsx`, реальные store и адаптер с хранилищем в памяти):
1. **Цикл сохранения:** лайк, создание плейлиста, добавление трека, Follow артиста, Save альбома, отметка «скачано», подписка на жанр, сортировка и вид Library → «перезапуск» (новый экземпляр store на том же хранилище) → всё восстановлено.
2. **`Set`:** `Set` ↔ массив без потерь и с сохранением порядка.
3. **Невалидный JSON:** стартовые данные и копия в `:corrupt`.
4. **Частично невалидный снимок:** отбрасываются только плохие записи.
5. **Ссылки на несуществующий каталог** отбрасываются.
6. **Миграция:** миграция v0 (тестовый «старый» формат) → v1.
7. **Версия из будущего:** данные не перезаписываются.
8. **Ошибка записи** (хранилище бросает исключение): приложение продолжает работать в памяти.
9. **Пропуск одинаковых записей:** 100 обновлений позиции плеера без изменения лайков → 0 лишних записей.
10. **SSR:** без `window` адаптер работает в памяти и не бросает исключений.

Существующие тесты store не меняются по смыслу; если `persist` меняет порядок инициализации, они адаптируются.

**Expo Web, 390 px:**
- Лайк, создание плейлиста, Follow, Save, отметка «скачано», сортировка и сетка Library → перезагрузка страницы → всё на месте.
- Вручную повредить значение в `localStorage` через DevTools → приложение загружается, повреждённая копия сохранена в `:corrupt`.
- Нет мигания Library при перезагрузке.
- Консоль без ошибок.

**Нативно:** не проверяется (нет симуляторов); в отчёте — явно.

Плюс typecheck, lint, все тесты, сборка Expo Web (статический рендер не должен падать), `git diff -- apps/api` пуст, локальный коммит без push.

## 10. Риски

| Риск | Мера |
|---|---|
| Частые записи из плеера | Пропуск одинаковых строк в адаптере (тест 9) |
| Статический рендер обращается к `window` | SSR-проверка в адаптере, хранилище в памяти на сервере (тест 10) |
| Обложки-`require` между сборками | Сохранение `coverKey`, а не `coverUri` |
| Стартовые данные «возвращаются» после изменения пользователем | После первой записи сохранённое состояние — источник истины (§4.4) |
| Откат приложения на старую версию | Блокировка записи при версии из будущего (тест 7) |
| Данные не шифруются | В хранилище нет секретов и платёжных данных (§3.3, §7.6) |
| Ограничения 2.2.0 против 3.x | 2.2.0 закреплена SDK 57; переход на 3.x — вместе с обновлением SDK |
| Нативное поведение не проверено | Явно указывается в отчёте |

2. **Активный фильтр Library** (All/Playlists/…): не сохранять (рекомендация) или сохранять?
3. **Повреждённые данные:** сохранять копию в `:corrupt` и начинать со стартовых данных (рекомендация) или просто сбрасывать?
4. **Последний трек после перезапуска:** вне Фазы 3 (рекомендация) или показывать последний трек на паузе в мини-плеере?
